# ADR-001: Использование sessionStorage для хранения корзины и активных заказов гостя

## Контекст и постановка задачи

В текущей версии MVP веб-приложения «AutoDetailing Studio» отсутствует система регистрации и авторизации пользователей (личные кабинеты). Клиенты оформляют заказы в гостевом режиме. При этом пользователи часто оформляют заявки со смартфонов, где высок риск случайного обновления страницы (свайп вниз) или кратковременной потери сети. Необходимо было определить механизм сохранения промежуточного состояния (выбранные услуги, черновик контактных данных и список только что отправленных заказов для редактирования), чтобы данные не терялись при перезагрузке страницы, но при этом соблюдалась приватность клиентов. Как и где мы должны хранить сессионные данные гостя? (Связанное требование: REQ-INT-004).

## Драйверы решения

- Устойчивость к случайной перезагрузке страницы (F5) без потери введенных данных.
- Приватность: данные клиента и автомобиля не должны «зависать» в браузере навсегда, если устройство используется несколькими людьми.
- Снижение нагрузки на сервер: минимизация хранения пустых или «брошенных» корзин на бэкенде.
- Отсутствие системы аутентификации (нет явной кнопки «Выйти»).
- Простота реализации в рамках MVP.

## Рассмотренные варианты

- Вариант 1: Хранение состояния в sessionStorage браузера
- Вариант 2: Хранение состояния в localStorage браузера
- Вариант 3: Использование HTTP Cookies и серверных сессий (Redis/Memcached)

## Итог решения

Выбранный вариант: «Вариант 1: Хранение состояния в sessionStorage браузера», потому что он обеспечивает надежную защиту от потери данных при обычном обновлении страницы (выполняя требование REQ-INT-004), но при этом автоматически очищает всю информацию при закрытии вкладки. Это гарантирует безопасность персональных данных гостя на общих устройствах без необходимости внедрять сложную логику аутентификации и очистки сессий.

### Последствия

- Хорошо, потому что не требует настройки инфраструктуры серверных сессий и снижает нагрузку на БД.
- Хорошо, потому что механизм встроен в современные браузеры и легко интегрируется с состоянием React-приложения.
- Хорошо, потому что естественным образом решает проблему «выхода» (данные уничтожаются при закрытии вкладки).
- Плохо, потому что если пользователь случайно закроет вкладку браузера (а не просто обновит её), корзина и доступ к редактированию отправленных заявок будут безвозвратно утеряны.

### Подтверждение

Соблюдение данного решения верифицируется с помощью демонстрационного тестирования пользовательского сценария (test-case: `tests/session_storage.md`):
1. Добавление услуг в корзину и ввод имени.
2. Принудительное обновление страницы (F5) — данные должны остаться на месте.
3. Копирование URL, закрытие текущей вкладки и открытие ссылки в новой вкладке — корзина должна оказаться пустой.

## Плюсы и минусы вариантов

### Вариант 1: Хранение состояния в sessionStorage браузера

Синхронное API браузера, сохраняющее строковые данные в рамках жизненного цикла одной вкладки.

- Хорошо, потому что данные переживают перезагрузку страницы.
- Хорошо, потому что данные автоматически удаляются при закрытии вкладки (высокая приватность для гостей).
- Хорошо, потому что реализация на React занимает минимум времени (через кастомный хук `useSessionStorage`).
- Плохо, потому что данные не шарятся между разными вкладками одного браузера.

### Вариант 2: Хранение состояния в localStorage браузера

Асинхронное/Синхронное хранилище браузера, где данные сохраняются бессрочно до ручной очистки.

- Хорошо, потому что данные сохраняются даже при полном закрытии и повторном открытии браузера.
- Хорошо, потому что состояние доступно во всех вкладках домена.
- Плохо, потому что данные остаются навсегда. Если клиент забудет их удалить, следующий пользователь устройства увидит его имя, телефон и номер машины (нарушение REQ-COMP-001).
- Плохо, потому что требует разработки механизма ручной инвалидации кэша.

### Вариант 3: Использование HTTP Cookies и серверных сессий

Создание анонимной сессии на бэкенде (Spring Session) при первом заходе, привязка корзины к Session ID, передаваемому через HTTP Only Cookie.

- Хорошо, потому что корзина хранится на сервере и недоступна для XSS-атак.
- Хорошо, потому что можно собирать аналитику по брошенным корзинам.
- Плохо, потому что значительно усложняет архитектуру MVP (требует хранения сессий в БД или Redis).
- Плохо, потому что требует реализации фоновой очистки (Job) истекших сессий из базы данных.

## Дополнительная информация

- Решение согласовано с Заказчиком на встрече по планированию архитектуры MVP (08.11.2026).
- Это решение напрямую реализует требование **REQ-INT-004: Сохранение состояния сессии** из Спецификации требований (SRS).
- В Архитектурном описании (SDD) данное решение зафиксировано под идентификатором **DEC-001-SessionStorage**.
- Решение может быть пересмотрено в версии 2.0 при внедрении личных кабинетов пользователей и полноценной JWT-авторизации, где корзина будет привязана к ID авторизованного клиента в БД.
