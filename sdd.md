## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ представляет собой Описание дизайна программного обеспечения (SDD) для веб-приложения «AutoDetailing Studio». Документ фиксирует выбранные архитектурные решения, структуру компонентов и модели динамического поведения системы на языке UML. Основная целевая аудитория документа — разработчики (фронтенд и бэкенд), архитекторы и проверяющий преподаватель. Документ служит техническим руководством для реализации требований, описанных в Спецификации требований (SRS).

### 1.2 Область применения {#12-subject-scope}

Проектируемая система: веб-приложение **«AutoDetailing Studio»** версии 0.2 (MVP). 
Документ охватывает проектирование клиент-серверной архитектуры приложения, включая React-фронтенд, REST API на базе Spring Boot и реляционную базу данных PostgreSQL, а также формализацию сценариев использования, потоков работ, переходов состояний заказа и межкомпонентного взаимодействия. В текущий дизайн **не входят** интеграции с внешними платежными шлюзами, системы SMS-уведомлений, сложная авторизация (Spring Security) и инфраструктура мобильных нативных приложений.

## 2. Обзор дизайна {#2-design-overview}

### 2.1 Задачи стейкхолдеров {#21-stakeholder-concerns}

- **Команда разработки**: заинтересована в четком разделении ответственности между слоями (фронтенд и бэкенд), прозрачности контрактов взаимодействия и понятной структуре DTO. (Адресуется точками зрения *Композиция*, *Логическое представление*, *Взаимодействие*).
- **Заказчик**: заинтересован в надежном хранении данных заказов, высокой скорости работы интерфейса и низкой стоимости поддержки MVP. (Адресуется точками зрения *Информация*, *Развертывание*, *Алгоритм*).
- **Преподаватель**: оценивает качество применения паттернов проектирования, полноту UML-моделирования динамического поведения и соблюдение стандартов. (Адресуется точками зрения *Паттерны*, *Взаимодействие*, *Динамика состояний*).

### 2.2 Выбранные точки зрения {#22-selected-viewpoints}

#### 2.2.1 Контекст {#221-context}
Система взаимодействует с двумя группами актёров: неавторизованными пользователями (**Клиентами**), которые через браузер просматривают каталог и оформляют заказы, и **Администраторами** студии, управляющими каталогом и статусами заявок. Внешние системы (платежи, почта) в текущем контексте отсутствуют.

#### 2.2.2 Композиция {#222-composition}
Система состоит из трех основных контейнеров:
1. **SPA Client** (React + Vite) — отвечает за рендеринг UI и хранение сессионного состояния (`sessionStorage`).
2. **Web API** (Spring Boot) — предоставляет REST endpoints, содержит бизнес-логику обработки заказов.
3. **Database** (PostgreSQL) — обеспечивает персистентное хранение состояния сущностей.

#### 2.2.3 Логическое представление {#223-logical}
Бэкенд спроектирован на основе строгой многослойной архитектуры (Layered Architecture):
- **Controllers** (HTTP-маршрутизация, прием JSON).
- **Services** (Бизнес-логика, транзакции).
- **Repositories** (Интерфейсы Spring Data JPA для доступа к данным).
- **Domain/Entities** (JPA сущности базы данных).

#### 2.2.4 Физическое представление {#224-physical}
Все узлы разворачиваются на едином физическом/виртуальном сервере под управлением Docker. Используется виртуальная сеть Docker bridge для изоляции взаимодействия между API и БД (порт 5432 закрыт от внешнего мира, порт 8080 проброшен наружу).

#### 2.2.5 Структура {#225-structure}
Взаимодействие компонентов происходит строго направленно: Фронтенд делает AJAX-запросы к Контроллерам Бэкенда -> Контроллеры вызывают Сервисы -> Сервисы используют Мапперы и Репозитории -> Репозитории обращаются к СУБД.

#### 2.2.6 Зависимости {#226-dependency}
- Фронтенд зависит от относительного пути `/api` (ожидает, что статика раздается тем же сервером, либо настроен Proxy в режиме разработки).
- Spring Boot зависит от доступности PostgreSQL (используется healthcheck `pg_isready` при запуске).

#### 2.2.7 Информация {#227-information}
Доменная модель включает сущности:
- `Customer` (Имя, телефон).
- `Car` (Марка, модель, госномер, ссылка на `Customer`).
- `Order` (Статус, дата, адрес, ссылка на `Customer` и `Car`).
- `OrderItem` (Цена, количество, ссылка на `Order` и `DetailingService`).
- `DetailingService` (Справочник услуг с базовой ценой).

#### 2.2.8 Интерфейс {#228-interface}
API реализован в архитектурном стиле REST. Обмен данными производится в формате `application/json`. Формализованный контракт описан спецификацией OpenAPI/Swagger, доступной по маршруту `/api-docs`.

#### 2.2.9 Взаимодействие {#229-interaction}
Сквозное взаимодействие компонентов системы формализовано на UML-диаграмме последовательности (`VIEW-006`):
1. UI отправляет `POST /api/customers` -> получает `customerId`.
2. UI отправляет `POST /api/cars` с `customerId` -> получает `carId`.
3. UI отправляет `POST /api/orders` с `customerId`, `carId` и списком услуг -> получает `OrderResponseDTO`.
4. В случае успеха UI сохраняет заказ в локальный `sessionStorage`.
5. Администратор меняет статус заказа через `PATCH /api/orders/{id}/status`.

#### 2.2.10 Алгоритм {#2210-algorithm}
- **Инициализация каталога:** при запуске приложения `DetailingServiceDataInitializer` проверяет количество записей в таблице услуг (`count()`). Если результат равен 0, создаются 8 базовых сущностей через `saveAll()`.
- **Поток оформления и сопровождения заказа:** детальная логика ветвлений, проверок валидации и обработки ошибок описана на UML-диаграмме активностей (`VIEW-004`).

#### 2.2.11 Динамика состояний {#2211-state-dynamics}
Сущность `Order` обладает собственным конечным автоматом состояний (`VIEW-005`). Состояния: `New` -> `Processing` -> `Completed` или `Cancelled` (`CANCELED`). Переходы инициируются при создании заявки, принятии её в работу, согласованной отмене и завершении оказания услуг.

#### 2.2.12 Параллелизм {#2212-concurrency}
Доступ к базе данных управляется пулом соединений (HikariCP). Пакетное создание заказов (bulk) защищено декларативными транзакциями `@Transactional(rollbackFor = Exception.class)`, что гарантирует консистентность данных при параллельных запросах или сбоях.

#### 2.2.13 Паттерны {#2213-patterns}
- **MVC** (Model-View-Controller) — базовый архитектурный паттерн Spring Web.
- **DTO** (Data Transfer Object) — изоляция структуры БД от внешнего API.
- **Facade** — использование сервисов как фасадов для сложных операций над несколькими репозиториями.
- **Repository** — абстракция работы с БД через Spring Data.

#### 2.2.14 Развёртывание {#2214-deployment}
Система упаковывается с помощью многоэтапной (multistage) сборки Dockerfile: на первом этапе собирается бандл Vite, на втором он копируется в директорию `src/main/resources/static` Spring Boot, на третьем компилируется итоговый `.jar`. Запуск оркестрируется через `docker-compose.yml`.

#### 2.2.15 Ресурсы {#2215-resources}
Приложение оптимизирует запросы к БД с помощью пагинации (`page`, `size`). Введено жесткое ограничение: размер страницы не может превышать 50 записей (реализуется на уровне логики сервиса), что защищает систему от исчерпания оперативной памяти.

  - `services` (бизнес-логика, транзакционность).
  - `repositories` (Spring Data JPA интерфейсы).
  - `entities` (JPA аннотированные классы).
  - `dto` (структуры запросов и ответов).

- **ID**: VIEW-002-Deployment-Container
- **Title**: Топология развертывания через Docker
- **Viewpoint**: Развертывание

Контейнеры общаются по bridge network. Конфигурация зависит от переменных окружения (`SPRING_DATASOURCE_*`).

- **ID**: VIEW-003-UseCase-Model
- **Title**: Диаграмма вариантов использования (UML Use Case Diagram)
- **Viewpoint**: Контекст / Функциональная модель
- **Representation**: Определяет границы системы и распределение сценариев между двумя актёрами:
  - **Клиент** инициирует `UC-01 Просмотр каталога услуг`, `UC-02 Выбор услуг`, `UC-03 Ввод данных`, `UC-04 Оформление заказа` (связано отношением `<<include>>` с выбором услуг и вводом данных) и `UC-05 Просмотр активных заказов клиента`.
  - **Администратор** инициирует `UC-06 Изменение статуса заказа`, `UC-07 Управление каталогом услуг`, `UC-08 Просмотр всех заказов`, а также расширенные сценарии (`<<extend>>` к просмотру всех заказов): `UC-09 Фильтрация и поиск заказов`, `UC-10 Отмена заказа` и `UC-11 Редактирование данных`.
  - Графическая схема: `AutoDetailing_UseCase.png`.
- **More Information**: Детальные текстовые потоки событий приведены в `Use-Case-Specifications.md`.

- **ID**: VIEW-004-Activity-Flow
- **Title**: Диаграмма активностей оформления и сопровождения заказа (UML Activity Diagram)
- **Viewpoint**: Алгоритм
- **Representation**: Моделирует пошаговый поток действий от открытия каталога до завершения работы с заказом:
  1. Проверка выбора услуг (`Услуги выбраны?`): при отрицательном результате переход к оформлению блокируется с возвратом к выбору.
  2. Проверка корректности формы (`Валидация пройдена?`): при ошибке выводятся сообщения валидации с возвратом к вводу данных.
  3. Создание записи в БД и проверка ответа сервера (`Заказ создан?`): при сбое выводится ошибка сервера и процесс завершается.
  4. При успешном создании карточка заказа сохраняется в `sessionStorage`, открывается экран заказов клиента и выполняется проверка возможности отмены (`Заказ в работе?` -> `Отменить заказ?`).
  - Графическая схема: `AutoDetailing_Activity.png`.
- **More Information**: Реализует сценарии `UC-01`–`UC-05` и требования REQ-FUNC-002, REQ-FUNC-003, REQ-INT-004.

- **ID**: VIEW-005-Order-StateMachine
- **Title**: Диаграмма состояний жизненного цикла заказа (UML State Machine Diagram)
- **Viewpoint**: Динамика состояний
- **Representation**: Описывает допустимые состояния сущности `Order` и триггеры переходов:
  - Начальный переход при оформлении заказа переводит сущность в состояние `New`.
  - Из `New` возможен переход в `Processing` (событие *«Начало выполнения»*) либо в конечное состояние `Cancelled` (событие *«Отмена до начала»*).
  - Из `Processing` возможен переход в `Completed` (событие *«Заказ выполнен»*) либо в `Cancelled` (событие *«Согласованная отмена»*).
  - Примечание к состоянию `Processing` фиксирует бизнес-правило: после принятия заказа в работу самостоятельное редактирование данных клиентом блокируется.
  - Графическая схема: `AutoDetailing_State.png`.
- **More Information**: Реализует прецедент `UC-06` и требование REQ-FUNC-005 из SRS.

- **ID**: VIEW-006-Sequence-Interaction
- **Title**: Диаграмма последовательности обработки заказа (UML Sequence Diagram)
- **Viewpoint**: Взаимодействие
- **Representation**: Отображает хронологический обмен сообщениями между актёрами (`Клиент`, `Администратор`), фронтендом (`Web UI`), слоями Spring Boot (`CustomerController`, `CarController`, `OrderController`, `OrderService`, `Repositories`) и СУБД `PostgreSQL`:
  - **Сценарий 1 (Оформление заказа):** последовательные HTTP-запросы `POST /api/customers`, `POST /api/cars` и `POST /api/orders` с выполнением SQL-операций `INSERT`, валидацией услуг в сервисе и сохранением результата в `sessionStorage`.
  - **Сценарий 2 (Смена статуса заказа):** вызов `PATCH /api/orders/{id}/status` администратором, выборка заказа (`SELECT`), обновление статуса на `PROCESSING` (`UPDATE`) и возврат `200 OK`.
  - Графическая схема: `AutoDetailing_Sequence.png`.
- **More Information**: Реализует сценарии `UC-04` и `UC-06` (REQ-INT-006, REQ-FUNC-003).

## 4. Решения {#4-decisions}

- **ID**: DEC-001-SessionStorage
- **Title**: Хранение черновика и активных заказов в SessionStorage
- **Context**: В MVP-версии отсутствует подсистема аутентификации пользователей. Требовалось найти способ сохранять выбранные услуги и карточки созданных заказов при случайном обновлении страницы на мобильном устройстве (REQ-INT-004).
- **Options**: 
  - Использовать Cookie (сложнее в работе с объектами).
  - Использовать LocalStorage (данные останутся навсегда, что приведет к путанице для публичных устройств).
  - Использовать SessionStorage (данные живут в рамках одной вкладки браузера).
- **Outcome**: Выбран вариант «SessionStorage», потому что он обеспечивает достаточную защиту от потери данных при F5, но автоматически очищается при закрытии вкладки, что идеально подходит для гостевого режима.

- **ID**: DEC-002-Transaction-Management
- **Title**: Раздельное создание сущностей через API фронтенда
- **Context**: Формирование заказа требует сохранения данных Клиента, Автомобиля и Заказа (REQ-FUNC-003, REQ-FUNC-004).
- **Options**:
  - Единый огромный монолитный JSON запрос.
  - Цепочка REST вызовов: создание клиента -> создание авто -> создание заказа.
- **Outcome**: Выбран вариант «Цепочка REST вызовов», потому что это делает API более атомарным и переиспользуемым, позволяя в будущем легко добавить поиск существующих клиентов перед созданием заказа. 

- **ID**: DEC-003-Multistage-Docker
- **Title**: Раздача статики React силами Spring Boot
- **Context**: Развертывание системы на одном хосте для MVP.
- **Options**:
  - Поднять отдельный контейнер Nginx для фронтенда.
  - Собрать фронтенд в `dist` и перенести в `static` папку Spring Boot для раздачи одним JAR-файлом.
- **Outcome**: Выбран вариант «Раздача статики через Spring Boot», потому что это снижает потребление ресурсов и упрощает `docker-compose` конфигурацию (убирает проблему настройки CORS в production).
