## 1. Введение {#1-introduction}
 
### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ представляет собой Спецификацию требований к программному обеспечению (SRS) для веб-приложения «AutoDetailing Studio». Его главная задача - четко определить границы проекта и зафиксировать **ЧТО** именно должна делать система, оставляя при этом пространство для инженерных решений относительно того, **КАК** это будет реализовано.

Документ выступает главным ориентиром для всех участников проекта, определяя зоны их ответственности:
- **Команда разработки** - использует спецификацию как основу для декомпозиции задач и реализации функциональности;
- **Инженеры по тестированию** - опираются на требования при составлении тест-планов и критериев приемки;
- **Заказчик** – сверяет по документу, насколько итоговый продукт закрывает его бизнес-потребности;
- **Преподаватель** - проводит оценку качества проектирования и проверку артефактов на протяжении жизненного цикла продукта.

Связанные документы: бизнес-требования от Заказчика, а также модель требований на языке SysMLv2 и структурные диаграммы пользовательских интерфейсов, созданные на этапе проектирования.

### 1.2 Область применения продукта {#12-product-scope}

**«AutoDetailing Studio»** 0.1 - веб-приложение для просмотра каталога услуг по уходу за автомобилем и онлайн-оформления заказов. Пользователь изучает услуги студии, формирует заказ, передает данные о своем автомобиле и отслеживает статус заявки.

**Входит в область применения:**
- каталог услуг детейлинга (описание, цены, изображения);
- выбор одной или нескольких услуг для оформления;
- форма создания заказа (сбор данных о клиенте и автомобиле);
- просмотр активных заказов пользователя и их редактирование;
- поиск и фильтрация заказов;
- адаптивный веб-интерфейс для работы со смартфона и ПК.

**Не входит в область применения (в текущей версии):**
- онлайн-оплата услуг через платежные шлюзы;
- SMS или Email-рассылки и уведомления;
- бронирование услуг на конкретное время (календарь записи);
- полноценное нативное мобильное приложение (iOS/Android);
- сложная CRM-система и интеграция с внешними кассовыми аппаратами.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

**«AutoDetailing Studio»** - новый самостоятельный продукт. Ранее процесс записи на услуги детейлинга происходил в основном по телефону или через социальные сети, что приводило к потере данных, ошибкам в записи марок автомобилей и непониманию итоговой стоимости клиентом. Приложение должно автоматизировать этот процесс, объединив прозрачный каталог услуг, удобную форму сбора данных об автомобиле и систему управления заказами в одном веб-интерфейсе.

**Внешние системы и зависимости:**
- Продукт является независимым клиент-серверным приложением (React + Spring Boot), не требующим на этапе MVP обязательных интеграций с внешними CRM или платежными шлюзами.

### 2.2 Функции продукта {#22-product-functions}

Основные функциональные возможности веб-приложения «AutoDetailing Studio»:

- Просмотр каталога услуг детейлинга (цены, описания).
- Выбор нескольких услуг для формирования корзины (черновика заказа).
- Оформление заказа с указанием данных клиента (имя, телефон) и автомобиля (марка, модель, гос. номер).
- Сохранение активных заказов в сессии пользователя.
- Редактирование данных отправленного заказа и его отмена.
- Постраничный поиск и фильтрация заказов (функционал API).
- Управление статусами заказа (Новый, В обработке, Завершен, Отменен).
- Адаптивный интерфейс для смартфона и ПК.

### 2.3 Ограничения продукта {#23-product-constraints}

При разработке веб-приложения «AutoDetailing Studio» должны соблюдаться следующие ограничения:

- **Только веб-версия:** Система реализуется исключительно как веб-приложение (без нативных приложений для iOS и Android).
- **Язык интерфейса:** Пользовательский интерфейс должен быть полностью на русском языке.
- **Без расписания:** Привязка заказа к точному времени в календаре не входит в MVP (заявки обрабатываются менеджером).
- **Без онлайн-платежей:** Покупка услуг внутри приложения не предусмотрена, оплата происходит по факту выполненных работ.
- **Законодательство:** Система должна соответствовать Закону РБ «О защите персональных данных» при сборе номеров телефонов и данных авто.
- **Технологический стек:** Бэкенд-часть должна быть реализована на языке **Java** с использованием фреймворка **Spring Boot**. Фронтенд-часть должна быть реализована с использованием библиотеки **React**. База данных — **PostgreSQL**.

### 2.4 Характеристики пользователей {#24-user-characteristics}

Система различает пользователей по их роли и правам доступа к функционалу. Основные классы пользователей представлены в таблице:

|          Роль              |             Описание             | Уровень подготовки|                             Права доступа                                |
| :------------------------- | :----------------------------- | :---------------- | :-------------------------------------------------------------------- |
| **Гость / Клиент**         | Посетитель студии              | Базовый           | Просмотр каталога, оформление заказа, редактирование/отмена своих заказов |
| **Администратор**          | Сотрудник автостудии           | Средний           | Управление каталогом услуг, просмотр всех заказов, смена статусов заказов |

**Особенности поведения и UX:**
- Клиенты часто открывают сайт с мобильных устройств находясь в автомобиле - требуется адаптивный дизайн (Mobile-First) и крупные элементы форм.
- Форма ввода данных автомобиля должна быть максимально простой для минимизации ошибок при вводе гос. номеров.

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

**Допущения (предполагаемые условия):**
- **Браузеры:** Пользователи используют современные веб-браузеры с поддержкой HTML5, CSS3 и JavaScript, а также включенным `sessionStorage` (влияние при нарушении: заказы не будут сохраняться после обновления страницы).
- **Интернет:** Для отправки заказа и загрузки каталога требуется стабильное соединение.
- **Хостинг:** Серверная инфраструктура обеспечивает постоянный доступ к REST API.

**Зависимости (внешние системы и сервисы):**
- Развертывание системы зависит от контейнеризатора **Docker** и **Docker Compose**.

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

**REQ-INT-001: Главная страница и каталог**
- **Title:** Информация о студии и выбор услуг.
- **Statement:** Система должна предоставлять главную страницу с описанием преимуществ студии и каталогом услуг. Каталог должен позволять выбирать одну или несколько позиций.
- **Rationale:** Клиент должен ознакомиться с ценами и выбрать нужные услуги до перехода к оформлению.
- **Acceptance Criteria:** Каталог загружается из API; выбранные услуги визуально выделяются; доступна кнопка перехода к оформлению.
- **Verification Method:** Demonstration.

**REQ-INT-002: Интерфейс «Оформление заказа»**
- **Title:** Сбор данных клиента и автомобиля.
- **Statement:** Система должна предоставлять форму для ввода имени, телефона клиента, а также марки, модели и гос. номера автомобиля.
- **Rationale:** Для оказания услуги студии необходима идентификация авто и контакт с владельцем.
- **Acceptance Criteria:** Форма содержит валидацию полей; отображает выбранные ранее услуги; отправляет данные на сервер по нажатию кнопки.
- **Verification Method:** Demonstration.

**REQ-INT-003: Интерфейс «Активные заказы»**
- **Title:** Управление заявками пользователя.
- **Statement:** Система должна предоставлять экран со списком заказов, оформленных пользователем, с возможностью редактирования данных авто/клиента или удаления (отмены) заказа.
- **Rationale:** Клиент должен иметь возможность исправить ошибку в номере машины или отказаться от услуги.
- **Acceptance Criteria:** Карточки заказов отображают текущий статус; действия "Сохранить изменения" и "Удалить заказ" корректно отрабатывают через API.
- **Verification Method:** Demonstration.

**REQ-INT-004: Сохранение состояния сессии**
- **Title:** Локальное хранение черновика.
- **Statement:** Система должна сохранять выбранные услуги, введенные в форму данные и список оформленных заказов в `sessionStorage` браузера.
- **Rationale:** Предотвращение потери данных при случайной перезагрузке страницы на смартфоне.
- **Acceptance Criteria:** При обновлении вкладки (F5) данные формы и карточки заказов восстанавливаются.
- **Verification Method:** Test.

**Юзабилити и доступность:** Интерфейс должен соответствовать принципам адаптивного дизайна (Mobile-First) и обеспечивать понятные состояния ошибок (например, показ уведомлений при недоступности сервера). Структурные диаграммы экранов приведены в разделе 5.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

**REQ-INT-005: Адаптивность под экраны**
- **Title:** Поддержка мобильных устройств и ПК.
- **Statement:** Система должна корректно отображаться на устройствах с разрешением экрана от 320px до 2560px.
- **Rationale:** Пользователи часто оформляют заявки из салона автомобиля со смартфона.
- **Acceptance Criteria:** Верстка элементов управления (кнопки, инпуты) не ломается на мобильных экранах.
- **Verification Method:** Test.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**REQ-INT-006: REST API для связи Frontend и Backend**
- **Title:** Взаимодействие клиента и сервера.
- **Statement:** Бэкенд-часть должна предоставлять REST API (в формате JSON) для взаимодействия с React-фронтендом по маршрутам `/api/customers`, `/api/cars`, `/api/orders` и др.
- **Rationale:** Обеспечивает разделение клиентской и серверной логики.
- **Acceptance Criteria:** Все запросы возвращают корректные HTTP-статусы (200, 201, 204, 400).
- **Verification Method:** Test (Postman).

**REQ-INT-007: Интеграция с СУБД**
- **Title:** Хранение данных.
- **Statement:** Система должна использовать базу данных PostgreSQL для постоянного хранения информации о клиентах, авто, услугах и заказах.
- **Rationale:** Гарантия сохранности бизнес-данных.
- **Acceptance Criteria:** Приложение успешно подключается к БД через JDBC с использованием учетных данных из переменных окружения.
- **Verification Method:** Demonstration.

### 3.2 Функциональные требования {#32-functional}

#### Каталог и оформление

**REQ-FUNC-001: Инициализация и просмотр каталога**
- **Statement:** При первом запуске система должна автоматически инициализировать базовый список услуг (если база пуста) и предоставлять его для просмотра в UI.
- **Rationale:** Предоставление контента пользователю «из коробки» без необходимости ручного администрирования на старте.
- **Acceptance Criteria:** При пустой таблице создаются базовые услуги (Мойка, Полировка и т.д.); фронтенд отображает их списком.
- **Verification Method:** Test

**REQ-FUNC-002: Выбор услуг**
- **Statement:** Система должна позволять пользователю выбирать одну или несколько услуг из каталога для последующего оформления.
- **Rationale:** Клиент может заказать комплекс услуг.
- **Acceptance Criteria:** Невозможно перейти к оформлению с пустой корзиной. Выбранные услуги фиксируют свою базовую цену.
- **Verification Method:** Test

**REQ-FUNC-003: Создание заказа (Клиент + Автомобиль + Услуги)**
- **Statement:** При оформлении система должна последовательно сохранять данные нового клиента, данные его автомобиля, а затем формировать заказ со списком позиций и статусом `NEW`.
- **Rationale:** Нормализованное хранение сущностей в базе данных.
- **Acceptance Criteria:** Заказ успешно связывается с ID клиента и ID автомобиля.
- **Verification Method:** Test

#### Управление заказами

**REQ-FUNC-004: Управление активными заказами (UI)**
- **Statement:** Система должна позволять пользователю просматривать свои отправленные заявки, изменять контактные данные или отменять заказ.
- **Rationale:** Гибкость и исправление пользовательских ошибок.
- **Acceptance Criteria:** Изменение данных отражается в БД; отмена удаляет карточку из интерфейса.
- **Verification Method:** Demonstration

**REQ-FUNC-005: Жизненный цикл заказа (API)**
- **Statement:** Бэкенд должен поддерживать изменение статусов заказа: `NEW`, `PROCESSING`, `COMPLETED`, `CANCELED`.
- **Rationale:** Административный учет выполнения работ.
- **Acceptance Criteria:** Вызов PATCH-запроса изменяет статус заказа на переданный.
- **Verification Method:** Test

**REQ-FUNC-006: Поиск и фильтрация заказов (API)**
- **Statement:** Система должна предоставлять API для постраничного поиска заказов по имени клиента, названию услуги или статусу.
- **Rationale:** Администратор должен легко находить нужную заявку среди тысяч других.
- **Acceptance Criteria:** API возвращает корректную страницу данных (page, size) и метаданные пагинации.
- **Verification Method:** Test

**REQ-FUNC-007: Пакетные транзакционные операции (API)**
- **Statement:** Бэкенд должен предоставлять возможность пакетного создания заказов, обеспечивая целостность данных через транзакции СУБД.
- **Rationale:** Защита от частичного сохранения некорректных данных при массовых операциях.
- **Acceptance Criteria:** При возникновении ошибки в одной из заявок пакета в рамках транзакции, весь пакет откатывается (Rollback).
- **Verification Method:** Test

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

**REQ-PERF-001: Время отклика API**
- **Statement:** Среднее время обработки запросов к REST API (создание заказа, загрузка каталога) не должно превышать **300 мс**.
- **Rationale:** Быстрый отклик обеспечивает плавность работы пользовательского интерфейса.
- **Acceptance Criteria:** 95% запросов обрабатываются быстрее 300 мс при стандартной нагрузке.
- **Verification Method:** Analysis

**REQ-PERF-002: Ограничение размера выборки**
- **Statement:** Система должна ограничивать максимальный размер запрашиваемой страницы данных при поиске заказов (не более 50 записей за запрос).
- **Rationale:** Защита базы данных от перегрузки тяжелыми запросами.
- **Acceptance Criteria:** Если клиент запрашивает `size=1000`, API принудительно устанавливает `size=50`.
- **Verification Method:** Test

#### 3.3.2 Безопасность {#332-security}

**REQ-SEC-001: Валидация входящих данных**
- **Statement:** Все пользовательские данные, поступающие на бэкенд, должны проходить серверную валидацию (Bean Validation).
- **Rationale:** Защита от записи некорректных данных и нарушения целостности базы.
- **Acceptance Criteria:** Попытка создать клиента без имени или с отрицательной ценой услуги возвращает статус `400 Bad Request` с описанием ошибки.
- **Verification Method:** Test

**REQ-SEC-002: Защита от SQL-инъекций**
- **Statement:** Взаимодействие с базой данных должно выполняться строго через параметризованные запросы ORM (JPA/Hibernate).
- **Rationale:** Предотвращение выполнения произвольного вредоносного кода SQL.
- **Acceptance Criteria:** Вредоносный ввод в формы не приводит к SQL Injection.
- **Verification Method:** Inspection

**REQ-SEC-003: Безопасное управление секретами**
- **Statement:** Учетные данные для подключения к БД (URL, логин, пароль) не должны храниться в исходном коде.
- **Rationale:** Предотвращение утечки доступов.
- **Acceptance Criteria:** Настройки передаются исключительно через переменные окружения (`SPRING_DATASOURCE_*`).
- **Verification Method:** Inspection

#### 3.3.3 Надёжность {#333-reliability}

**REQ-REL-001: Безопасная инициализация**
- **Statement:** Механизм автозаполнения каталога не должен перезаписывать или удалять существующие услуги при перезапуске сервера.
- **Rationale:** Сохранение данных, измененных администратором.
- **Acceptance Criteria:** Инициализация запускается только если таблица услуг абсолютно пуста.
- **Verification Method:** Test

**REQ-REL-002: Целостность зависимостей запуска**
- **Statement:** Приложение не должно начинать обработку запросов до полной готовности базы данных.
- **Rationale:** Избежание ошибок подключения при старте.
- **Acceptance Criteria:** Контейнер бэкенда ожидает успешного health-чека PostgreSQL (`pg_isready`).
- **Verification Method:** Demonstration

#### 3.3.4 Доступность {#334-availability}

**REQ-AVAIL-001: Автоматический перезапуск**
- **Statement:** Контейнеры приложения и базы данных должны использовать политику автоматического перезапуска при сбоях.
- **Rationale:** Снижение времени простоя без вмешательства человека.
- **Acceptance Criteria:** В конфигурации Docker Compose указана политика `restart: unless-stopped`.
- **Verification Method:** Inspection

#### 3.3.5 Наблюдаемость {#335-observability}

**REQ-OBS-001: Мониторинг состояния (Health Check)**
- **Statement:** Система должна предоставлять эндпоинт для проверки статуса приложения.
- **Rationale:** Позволяет внешним системам мониторинга оценивать доступность сервиса.
- **Acceptance Criteria:** GET `/actuator/health` возвращает статус `UP`.
- **Verification Method:** Demonstration

**REQ-OBS-002: Структурированное логирование**
- **Statement:** Приложение должно использовать централизованную конфигурацию логирования, записывая ключевые события с отметкой времени и уровнем важности.
- **Rationale:** Упрощение отладки и поиска причин инцидентов.
- **Acceptance Criteria:** Логи пишутся согласно конфигурации (например, Logback), SQL-запросы логируются при включении соответствующего флага.
- **Verification Method:** Inspection

### 3.4 Соответствие стандартам {#34-compliance}

**REQ-COMP-001: Защита персональных данных**
- **Statement:** Сбор телефонных номеров и имен клиентов должен осуществляться с учетом применимого законодательства (Закон РБ «О защите персональных данных»).
- **Rationale:** Юридическая чистота использования продукта.
- **Acceptance Criteria:** Данные используются строго для связи по заказу, проект архитектурно позволяет реализовать политику удаления данных по запросу (CRUD-операции клиента присутствуют).
- **Verification Method:** Inspection

**REQ-COMP-002: Стандарты оформления кода**
- **Statement:** Исходный код Java должен проходить статический анализ на соответствие стилистическим стандартам (Checkstyle).
- **Rationale:** Поддержание чистоты и читаемости кодовой базы.
- **Acceptance Criteria:** Проект включает конфигурацию Checkstyle.
- **Verification Method:** Inspection

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

**REQ-INST-001: Контейнеризация**
- **Statement:** Бэкенд, фронтенд и база данных должны поставляться в Docker; запуск всей среды описывается в `docker-compose.yml`.
- **Rationale:** Простота и воспроизводимость развертывания на любом сервере.
- **Acceptance Criteria:** Команда `docker compose up --build` поднимает рабочую систему (порт 8080 для веб-доступа, 5432 для СУБД).
- **Verification Method:** Demonstration

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

**REQ-BUILD-001: Сборка бэкенда**
- **Statement:** Сборка Java-части должна осуществляться через Maven Wrapper, результат — исполняемый `Spring Boot JAR`.
- **Acceptance Criteria:** Команда `mvnw clean package` завершается успешно.
- **Verification Method:** Test

**REQ-BUILD-002: Сборка фронтенда**
- **Statement:** Сборка React должна выполняться инструментами npm/Vite.
- **Acceptance Criteria:** Билд создает бандл статических файлов в директории `dist`.
- **Verification Method:** Test

**REQ-BUILD-003: Объединенная поставка**
- **Statement:** При сборке контейнера файлы фронтенда должны копироваться в статические ресурсы бэкенда для раздачи единым сервером.
- **Rationale:** Избежание необходимости настраивать отдельный Nginx на этапе MVP.
- **Acceptance Criteria:** `Dockerfile` содержит multistage-сборку, объединяющую UI и API.
- **Verification Method:** Inspection

#### 3.5.3 Распределение {#353-distribution}

**REQ-DIST-001: Централизованное развертывание**
- **Statement:** Компоненты системы (приложение и СУБД) развертываются на едином хосте с использованием Docker Compose.
- **Acceptance Criteria:** Отсутствует необходимость в сложной микросервисной оркестрации.
- **Verification Method:** Inspection

#### 3.5.4 Сопровождаемость {#354-maintainability}

**REQ-MAINT-001: Многослойная архитектура**
- **Statement:** Бэкенд должен строго разделять ответственность на слои: контроллеры (API), сервисы (бизнес-логика), репозитории (БД) и DTO (передача данных).
- **Verification Method:** Inspection

**REQ-MAINT-002: Документация проекта**
- **Statement:** В корне репозитория должен присутствовать актуальный `README.md` с инструкциями по сборке и запуску.
- **Verification Method:** Inspection

#### 3.5.5 Повторное использование {#355-reusability}

**REQ-REUSE-001: Разделение логики и маппинга**
- **Statement:** Конвертация сущностей базы данных в DTO должна быть вынесена в отдельные компоненты-мапперы.
- **Verification Method:** Inspection

#### 3.5.6 Переносимость {#356-portability}

**REQ-PORT-001: Независимость от ОС**
- **Statement:** Приложение должно компилироваться и запускаться на платформах Windows, Linux и macOS благодаря Java 17 и Docker.
- **Verification Method:** Demonstration

#### 3.5.7 Стоимость {#357-cost}

**REQ-COST-001: Open Source стек**
- **Statement:** Проект должен использовать бесплатные технологии без коммерческих лицензий (Java, Spring, React, PostgreSQL).
- **Verification Method:** Inspection

- **Statement:** Перед разработкой сложной логики должен быть продемонстрирован сквозной сценарий: передача данных от UI к REST API и их успешное сохранение в PostgreSQL.
- **Rationale:** Валидация интеграции выбранного технологического стека.
